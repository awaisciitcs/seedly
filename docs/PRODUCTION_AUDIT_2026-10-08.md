# Seedly production audit — 8 October 2026

**Release decision: NOT production-ready yet.** The identified public database exposures and reproducible application defects were fixed. Build, regression, database-fixture and HTTP checks passed. Required credentials, historical inventory reconciliation, notification activation and staging/browser verification remain open. No claim of zero vulnerabilities or complete end-to-end certification is made.

Reviewed the Next.js storefront, admin dashboard, API handlers, authorization, Supabase schema/functions/policies/Storage, checkout calculations, fulfillment/payment transitions, catalog editing, reviews, subscription preferences, notification adapters, maintenance scripts, dependency advisories and rollback tooling.

No customer order was created, cancelled, fulfilled, renumbered or paid during this audit. No email or WhatsApp message was sent. No private customer rows were exported or printed. ## Fixed findings

| Priority | Finding | Implemented behavior and verification |
| --- | --- | --- |
| Critical | Anonymous callers could execute the privileged order-creation RPC directly, bypassing application validation. | Both creator RPCs now require service_role. The secure wrapper rechecks the exact quoted total, shipping and pack prices inside the stock/order transaction. Public and normal authenticated execution are denied. SQL tests cover invalid quantities, foreign packs, stock failure and rollback after price changes. |
| Critical | Public Storage policies allowed catalog-image creation/modification/deletion and receipt insertion. | Catalog writes require active authenticated admin membership; anonymous receipt writes were removed. Product images accept JPG/PNG/WebP/GIF up to 5 MB; receipts stay private with their JPG/PNG/PDF limit. SQL role tests and live policy inspection passed. |
| High | Email/phone verification and predictable references could disclose order data; authorized responses contained internal secrets. | Guest lookup requires the private 64-character capability for every reference. Email/phone are not credentials. Customer responses omit retry fingerprints, token hashes, receipt paths and admin notes. Active administrators retain a cookie/RLS-protected preview. Private pages use no-store, no-referrer and noindex. |
| High | Fulfillment could jump stages; repeated cancellation or changed kit composition could restore the wrong stock. | Explicit forward transitions, payment verification, courier/tracking requirements and terminal-state protection are enforced in the database and application. Exact component reservations are recorded at order creation and released once. Cancellation and refund tests passed. |
| High | Admin identity could be linked by email; privileged clients could fall back to public keys or bypass RLS. | Explicit active Auth UUID links and OWNER/STAFF roles are required after getUser(). Admin reads/writes use the cookie session so RLS rechecks membership. Privileged clients require a private service-role key. Login remains reachable for disabled/non-admin users; password whitespace is preserved. |
| High | Catalog parent/variant/component updates were separate operations and could partially commit or overwrite changed stock. | One authenticated transactional save validates ownership, prices, sizes and components. Existing packs require expected update timestamps. Stale edits return conflicts; zero stock remains zero. Products/kits are archived to preserve order history. In-memory SQL tests passed. |
| High | A tracked script embedded an administrator password; maintenance scripts could mutate the archived database and force-push backups. | The password was removed from source. Test login now requires an explicitly supplied dedicated account. SQLite mutations require a disposable external copy plus an explicit flag. Backups require a private key, paginate protected rows, write outside the repository, report incomplete exports and never push Git or create misleading SQL restore statements. The local SQLite archive remains intact and was removed from the Git index. Historical exposure still requires action below. |
| High | Direct authenticated writes could bypass the order transaction; staff could bypass owner-only bank/settings APIs. | Browser sessions now have SELECT-only commerce access. Payment/fulfillment RPCs are narrowly guarded SECURITY DEFINER functions with fresh active membership checks and pinned empty paths. Staff settings writes are denied by RLS; owner settings writes remain allowed. Role/transaction fixtures and live grants passed. |
| Medium | A lost order response followed by refresh could create a fresh checkout identity. | An uncertain submission keeps its original key and frozen body in session storage. Recovery runs before fresh stock/expiry checks; ordered quantities are removed without clearing unrelated basket items. Corrupt storage is rejected and storage failures are handled. Tests cover retry, depleted stock, expiry, identity conflicts and preservation of other basket lines. |
| Medium | The admin drawer used PATCH against a POST-only status route and had no dispatch form. | POST actions now support separate preparation, packing and dispatch with explicit courier/tracking inputs. Audit notes and bank references use the correct request field. Native dialogs provide focus containment, Escape dismissal and scroll locking. Failed loads show an error instead of an endless spinner. |
| Medium | Admin catalog requests used anonymous reads and could omit drafts/archived products. Command search ignored its product query and could show stale responses. | Admin catalog/search reads use authenticated RLS, filter names/SKUs and cancel superseded requests. Known input errors are validated; database outages are reported as unavailable rather than empty success. |
| Medium | Spreadsheet exports could evaluate customer-entered formulas; money displays discarded fractional rupees. | CSV cells are quoted/escaped and formula prefixes are neutralized. Blob downloads replace raw data-URI concatenation. Currency uses exact minor-unit conversion with up to two decimals. Regression tests passed. |
| Medium | Reviews could forge verified-purchase badges; pending inserts requested forbidden SELECT access. | New reviews are always pending/non-demo/unverified, validate active targets, use authoritative titles and enforce integer ratings/bounded text. Pending inserts do not request a public SELECT. Policies also reject forged verified reviews. |
| Medium | Embedded JSON-LD could terminate its script context. | A shared serializer escapes tag-open characters and Unicode line separators while retaining valid JSON. Injection round-trip tests passed. |
| Medium | Email clients could unsubscribe a customer by prefetching a GET link; failed delivery was shown as sent. | GET renders confirmation only; same-origin POST changes preferences. Unconfigured delivery is recorded as failed/prepared with no sent timestamp. Notification errors cannot invalidate a committed order/state change. |
| Medium | Next.js and several transitive packages had published advisories. | Dependencies were pinned and updated; Next.js is 15.5.27, which addresses the cache-poisoning advisories. Production-only npm audit reports zero vulnerabilities. The remaining build-tool advisory is detailed below. |

## Advisor interpretation

The post-fix Supabase report contains no ERROR-level security finding. It still warns about the deliberately public capability-protected SECURITY DEFINER lookup and the authenticated membership helpers used by RLS and the tightly guarded authenticated payment/fulfillment transactions. These are narrow audited boundaries, not general public write functions. See [public definer guidance](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable) and [authenticated definer guidance](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable). Public checkout_sessions has RLS and no policy, intentionally denying access. The private sequence table is also deny-by-default with service-only grants. Leaked-password protection remains an open warning. Performance notices include overlapping authenticated read policies and newly added unused indexes; retain FK support indexes until measured workload justifies removal.
